# CAP-2044 — Pay Bills: validate amount before submitting a payment

**Type:** story · **Source:** mock · **URL:** —

## Summary

The Pay Bills one-time payment form needs to give customers clear inline feedback when they enter an unusable amount — non-numeric text, zero/negative values, or an amount that exceeds the selected account's balance — instead of letting the submission proceed with an unclear result, while still letting a valid, in-balance amount go through as it does today. This applies whether the form is reached directly or via a Saved Payee's quick-pay button, since quick-pay only preselects a payee and scrolls/focuses the same form.

| AC-2 | ✅ | Given the customer enters an amount of $0 or a negative number, then they should see an inline error and no payment should go through. |

| AC-4 | ✅ | Given the customer enters a valid amount within their balance, then the payment should submit successfully as it does today. |

## Edge Cases

- **EC-1** — Amount entered with more than 2 decimal places (e.g. "40.999"), as raised in dev1's comment.
  _Rationale: Neither the ACs nor the current implementation (src/data.js parseAmount, src/api/accountsApi.js payBill) round or reject extra decimal precision — the value is passed straight through as a float. Left untested, a fractional-cent payment could silently submit with no defined expected behavior._
- **EC-2** — Submitting the form with the amount field left empty.
  _Rationale: src/data.js parseAmount('') returns NaN, which follows the same code path as non-numeric input in accountsApi.js payBill. This is the same behavior as AC-1 but isn't explicitly called out, so it's worth a dedicated boundary check._
- **EC-3** — Amount entered exactly equal to the selected account's available balance.
  _Rationale: accountsApi.js payBill only rejects when 'amount > from.balance', so an exact-balance payment should succeed — AC-3 only specifies amounts "greater than" the balance, leaving this boundary unstated._
- **EC-4** — Amount entered with currency formatting such as "$1,234.56", surrounding whitespace ("  100  "), or thousands separators.
  _Rationale: src/data.js parseAmount strips '$', ',', and whitespace before parsing, so these should be accepted as valid amounts, not rejected as "non-numeric" — this distinction isn't spelled out in the ACs._
- **EC-5** — Account balance changes between page load and submit (e.g. a payment completes in another tab first), as raised by qa1's comment.
  _Rationale: accountsApi.js payBill re-reads balance from storage at submit time via loadState(), so the balance check is likely already fresh, but no AC or existing test confirms what message the customer sees in this scenario._
